# Data layer

Everything in this directory is **synthetic**. It is generated by the repository
itself and describes a fictional downtown district; none of it is empirical
curb, meter, citation or ridehail data, and no number here should be read as a
measurement of any real place.

| file | produced by | what it is |
|---|---|---|
| `curb_segments.csv` | `python scripts/generate_data.py` | curb inventory: one row per block face, with stall counts by regulation type, price and time limit |
| `demand.csv` | `python scripts/generate_data.py` | hourly arrival rates per vehicle class, after the time-of-day profile |
| `network.geojson` | `python scripts/generate_data.py` | intersections, street links and curb segment centroids in local metric coordinates |
| `observed_occupancy.csv` | `python -m src.calibration.calibrate --generate` | the synthetic "observed" occupancy series used as a calibration target |
| `observed_occupancy_meta.json` | same | the hidden ground-truth parameters, sensor noise and coverage used to generate it |

## Why the data layer is separate

The simulation builds its network from `config/network.yaml` at run time, so it
does not read these files. They exist to pin down the *schemas* an empirical
deployment would populate:

* a **curb inventory** keyed by segment, with capacity and regulation by type
* an **occupancy series** keyed by segment and time window
* a **demand table** keyed by class and hour

Swapping in real meter occupancy, a real curb inventory and real TNC trip
records is therefore a data-layer change - write a loader that produces these
same tables - rather than a change to the simulation engine, the calibration
routine or the optimizer.

## Regenerating

```bash
python scripts/generate_data.py                     # inventory, demand, geometry
python -m src.calibration.calibrate --generate      # synthetic observations
```
